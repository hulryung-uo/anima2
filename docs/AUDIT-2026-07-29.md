# Multi-team audit — 2026-07-29

Six review teams (architecture, roadmap, process, tests, economy, devil's-advocate) were
run against this repo, their top proposals adversarially verified (three were refuted or
corrected — including one fabricated roadmap citation the verify pass caught), then
synthesized. The devil's-advocate team was lost to an infrastructure error; the synthesis
rests on the other five. This document records the FINDINGS; none of the proposals below
are decisions until acted on.

## Verdict

Micro-level engineering is genuinely strong: differential live gates with honest verdicts
(losses and retractions reported as-is), provenance-wiped economics, a fail-closed
capability authority boundary, 1327 tests in under 4 seconds. What is not going well is
structural: the project keeps paying for ONE defect class — a single world-fact defined in
two places (decide rule vs capability gate; runner N vs runner N+1) synchronized only by
memory. Six live failures trace to it, and **the audit found a seventh, latent today**:
`mage_life.py`'s `fetch_gold` rule ignores the `PICKUP_RADIUS` and pack-cap its gate
enforces (the carpenter's fix was never back-ported). Meanwhile the flagship "Lives" run
on scripted cognition (`_LifeClient` echoes `decide_mode`'s choice as fake LLM JSON) with
no Phase-6 persistence wired in — so the AI-native showcase is currently a hand-written
FSM village whose live hours accumulate no society state — and both deployed craft loops
destroy value at vendor prices (throne −33g; dagger batch −25g once staged iron runs out;
an Ettin pays ~157g vs +10g for the best craft trip).

## Top risks

1. **The dominant failure class does not converge under the current process** — six
   incidents fixed one at a time; the seventh (mage fetch_gold) already exists.
2. **Lives bypass the LLM brain and Phase-6 persistence** — the differentiators sit idle
   while deterministic rules do everything.
3. **Craft loops are value-destroying by construction** — a society scaled on them decays
   to bankruptcy, and gold-per-life fitness would rank crafters below doing nothing.
4. **Resumability contract broken** — CLAUDE.md's "Next:" (~90 commits stale) contradicts
   AUTONOMY-ROADMAP.md §E; this session's live proofs live in uncommitted scratchpad
   scripts.
5. **Scaling cliff at ~3–4 concurrent agents** — hand-tuned pump budgets, insertion-order
   capability priority, string-key contracts across two memories per agent.

## Stale-UI wedge (2026-07-31, forge15-18)

A full-stack forge-pair verification found the ONE defect the whole autonomy stack was

- **forge15** (symptom): Pim wanted `fetch_iron` for 671 straight ticks with 38 delivered
  ingots at his feet and `ready=[]`. Sixteen readiness gates share one "idle UI" clause,
  so a SINGLE open surface refuses every capability at once. The disagreement detector

- **forge16** (identity): the pair status line gained a `ui=` field, and the next wedge
  said `ui=shopbuy` — a vendor BUY window left behind by a finished `buy_iron` trip, 357
  disagreement ticks. Not a gump: the first repair (gump-only) could not have helped.
- **forge18** (repair, live): the detector now REPAIRS on firing — closing a gump
  (`GumpResponse` button 0) or cancelling a vendor window (an EMPTY `BuyItems`/`SellItems`
  list, which ServUO answers with `EndVendorBuy`). Live: `** Pim: closing an unowned
  vendor BUY window **`, after which `buy_iron` was ADMITTED again — the wedge cleared and
  the economy resumed (+165g at that point, 88g banked over two deposits).

The wedge RECURRED later in the same run — `buy_iron` admitted, `ui=shopbuy`, the agent
motionless — and I called it a second, still-open defect while watching it. That was
premature: the repair deliberately waits while a goal owns the surface, and once that
goal closed the detector fired again, cancelled the window again, and the economy resumed
(gold 77 -> 112 -> 147; two repairs, two recoveries, final net **+235g at ~1900g/h** with
88g banked). So the shape is SELF-HEALING but slow: each recurrence costs one goal
lifetime before the repair may act.

**That gap is now CLOSED (commit `8cdd2f0`, current HEAD)**, and it was real: the buy FSM had
a timeout for a window that never ARRIVES but none for a window already open when it did not
expect one, so each recurrence spent requests the server ignores while a window is up, ran its
counter to `POPUP_TIMEOUT`, threw the trip away, and only THEN let the Life's repair act. Both
popup stages (`_buy_step`, `_sell_step` in `anima2/skills/market.py`) now inspect an
already-open window FIRST: if it belongs to the vendor we came for, USE it — skip straight to
the order, since it is the very window the popup was going to open; if it belongs to anyone
else, cancel it with an EMPTY item list, which is ServUO's `EndVendorBuy` (the same close the
Life-layer repair uses). The sell stage also cancels a stale BUY window, since either surface
blocks it. Belt and braces on purpose: the trip handles the case it can see, the Life handles
the case where no trip exists to see it.

This doc's own prescribed method was followed — reproduced offline against MockBody (which
models `shop_buy` and the empty-list cancel) rather than hunted live: three FSM-layer tests
(ours-is-used, stranger's-is-cancelled, and the no-window path unchanged), suite at 1404.

## Proposal 5 was WIRELESS — and proposal 1's defect class was still live (2026-08-02)

Two re-examinations of already-"done" work, both of which found the mechanism present and
the wiring absent. The pattern is worth naming on its own: **a proposal implemented at the
callee and never at the caller reads as landed from every angle except the one that
matters.** The implementation record above marks both #1 and #5 complete, honestly — the
code each describes does exist. **The gap is a different one for each, and an earlier
draft of this paragraph flattened them into "neither could be USED", which is false of #1
and contradicted by this document's own record of it:**

- **#5's channel could not be used at all.** No production site could pass a threshold, so
  nothing outside the tests ever did (details below).
- **#1's suite could be used, was used, and earned its keep** — implementation record #1
  above: it failed on the latent mage drift on its first run and later caught a genuinely
  dead `bank_gold` branch in a brand-new `TinkerLife` before that Life's first live run.
  Its defect is narrower and it is coverage: the suite was BLIND along three whole axes at
  once — every fixture injected a backpack, every knob was pinned at its module default
  (where rule and gate agree by construction), and both craft lattices pinned `craft_spot`
  to the player's own tile. Four distinct rule-vs-gate disagreement classes were sitting
  inside those blind spots — the three pack-absent fetches recorded below and the
  carpenter's craft, whose batch clause is reachable on a shipped runner today. A suite
  that runs and passes is not the same as a suite that looks.

**Proposal 5 ("Life thresholds → constructor parameters").** The record says
"`bank_reserve`/`econ_grace` params". True — and `LifeSpec.life_factory` was typed
`(body, persona, routes) -> Life`, `LifeRunner.run` called it with exactly those three
positional arguments, and both shipped factories in `village.py` were
`lambda body, persona, routes: ...`, which would have raised `TypeError` on any keyword. So
no production site could pass a threshold and none ever did — only tests, by constructing a
Life directly. The prerequisite the proposal existed to create ("for genome axes, bandit
tuning, and slow-loop steering to touch them") was therefore never created, and CLAUDE.md's
deferral precondition (a) was nominally satisfied by it. What closed the gap:

- `LifeSpec.knobs` (a dict forwarded as keyword arguments) and `LifeRunner.build_life()` —
  a NAMED seam, because `run()` needs a live shard, so a knob channel proved only by
  re-implementing that one line in a test is a channel asserted but not wired. Offline
  tests and the live path now call the same method.
- Both `village.py` `LifeSpec` factories take and forward `**knobs` — and, as of the same
  day, both `LifeSpec` RUNNERS grew the caller-side end of it:
  `run_carpenter_life(knobs=...)` / `run_woodsman_life(knobs=...)` pass
  `LifeSpec(knobs=dict(knobs or {}))`. Copied, not aliased: a sweep script that reuses one
  dict must not be able to retune a Life that is already built. Default `None` keeps every
  existing caller byte-identical. Five of the seven construction sites still have no entry
  point — follow-up 2.
- `anima2/knobs.py` — the ONE clamped read: `knob_int(memory, key, default)` for a knob a
  `decide` staticmethod must see (it can only see memory), `knob_param(value, default)` for
  one only `tick()` reads, `type(value) is int` so a `True` clamps instead of passing as 1.
  `skills/market.py::_bank_reserve` (name, signature, docstring intact) is now that read
  bound to its key. This generalizes the lesson the natural-deposit campaign paid for above
  — "the bank_reserve raw-vs-clamped read that recreated the rule-vs-gate drift class
  through the tuning knob itself" — so knob N+1 inherits it without anybody remembering.
- Two new knobs (`WarriorLife(disagreement_ticks=...)`, floor 1 because floor 0 makes
  `streak >= window` true every tick and a HEALTHY Life would then self-report and fire
  `_clear_stale_ui` on every tick; `TinkerLife(bank_trip_surplus=...)`), and `econ_grace`
  hardened through the same clamp — at **floor 2**, which is a correction: it shipped at
  `knob_param`'s default floor of 0, where every malformed write (`-1`, `2.5`, `True`,
  `"6"`) landed on a Life with NO hysteresis, the exact mid-equip failure `ECON_GRACE`
  exists to prevent, while the adjacent comment claimed the clamp ruled that out. Floor 1
  would not have fixed it either — `_econ_streak` is incremented before
  `streak < grace` is tested, so 0 and 1 both switch on the first tick. Each floor is now
  the smallest value that still does the job its knob exists for, and each is pinned by a
  test. Review-caught, offline.
- **The concordance suite was blind to knobs.** It pinned each knob at its module default,
  where rule and gate agree BY CONSTRUCTION — a rule-side-only conversion passed untouched.
  It now sweeps every lattice point at eight settings per knob (wired / tuned down / tuned
  up / absent / negative / float / bool / string), in BOTH directions: the malformed rows
  catch a raw rule-side read, and `tuned_up` catches the opposite shape, a rule that cannot
  see its own knob. 1404 → 1419 tests, ~0.08s → 0.49s — both figures are this bullet's
  state when it was written, not the shipped tree's; the `craft_spot` (×5) and vendor (×2)
  axes landed after this snapshot and the file finishes the round at **1.87s** (7 tests,
  the tinker alone 1.47s). Stated because the "Keep doing" list names the <4s offline
  suite as a practice to protect, so the per-file cost is the number that matters.

**Proposal 1's defect class, found still live in the readbacks.** Twenty hand-copied
observation readbacks across the five Life modules (plus four in `life_runner.py`) are now
one definition each in `anima2/obsview.py`. Merging them exposed a real readback defect,
not just duplication: `carpenter._owns`, `tinker._owns_tool` and `woodsman._has_axe` wrote

*The pre-existing hole, worth its own sentence because the new report would have shipped
dead through it:* `_ThrottledAgent` (the proxy `run_supply_pair` and
`run_artisan_mage_village` drive their Lives through) has no `__getattr__`, so
`_run_worker`'s `getattr(agent, "rule_gate_disagreement", None)` was unconditionally
`None` for the throttled carpenter and the throttled mage — **the two Lives that run their
economy agent nearly every tick were the two that could never print the disagreement
alarm.** Both self-reports now pass through explicitly.

**The mechanism, restated in one paragraph.** `decide_mode` is a pure function of
`(obs, memory)` — that purity is the property the ~150k-point concordance lattice rests
on — so it structurally cannot see the goal stack, and it answers `"hunt"` the instant the
world-fact its branch was keyed on flips. For every economy branch of all five Lives that
fact is something the transaction ITSELF changes: the goods leave the pack, the coin
moves, the pile is lifted. For a sale that instant is the moment the vendor TAKES the item
— mid-transaction, with the walk home still owed. `WarriorLife.tick` then ticks the OTHER
agent, and three things freeze together because all three only advance inside
`Agent.tick`: the capability FSM, the `cap_*_finished` markers it would have to write
(every capability `step` returns `RUNNING`, and `CapabilityGoalComplete` is a planner
skill selected on a LATER tick), and `GoalStack.expire_due`, whose deadline is counted in
that same agent's ticks. §3 above has the live numbers.

**What the fix does.** `WarriorLife.tick` gains an EXIT-edge rule, after the `econ_grace`
entry hysteresis and before `self.mode` is assigned: if `decide` answered `"hunt"` while a
frame is live on the economy stack, the mode is HELD at `"economy"` so the frame's owner
agent keeps being ticked and can finish what it started. Three deliberate non-changes ride
with it: **`decide_mode` is not touched** (all five stay pure, so the concordance lattice
and its `_NOT_DRIVEN_BY_THE_LIFE` equality are untouched); **`want=` is not rewritten** to
the held frame's capability, because fixing the `admitted=` lie by rewriting `want=` would
re-create the identical ambiguity on the other side; and **one agent per orchestrator tick
stays the rule** — follow-up 10's candidate (i), a second economy tick on the exit edge, is
exactly what was NOT done, since that is what would make "which agent ticks" conditional on
goal state and break the route/reflex cadence the extra-pump comment records. The one
addition is a pin: `_econ_streak` is held at `econ_grace` for the duration, so the tick a
transaction retires commits straight back to the economy instead of re-earning a
hysteresis that exists to filter a mid-equip transient, not a completed trade.

**The bound, and why it needed a third one.** The first implementation claimed the hold
was self-limiting on two bounds. It is not, and the review measured why:

1. **The FSM's give-up ladder** returns `mkt_phase` to `"craft"` and writes
   `cap_run_finished_goal_id`, which `CapabilityGoalComplete` closes as a FAILURE. This is
   the usual exit and it is the forge1/forge13 lifecycle fix doing its job — but
   `grep -rn cap_run_finished_goal_id anima2/` has exactly **two writers**,
   `skills/market.py:1529` (`SellItemCapability`) and `:1920` (`BankGoldCapability`).
   Every buy / tool-buy / craft / fetch / process / deliver frame has no ladder at all.
2. **The frame's own deadline**, via `GoalStack.expire_due` — reachable only because the
   hold keeps the economy agent ticking. But `CapabilityPolicy.deadline_can_expire` defers
   at an unsafe yield point, and every `*_can_yield` in `capabilities.py` carries the same
   unconditional "idle UI" clause — **all EIGHT of them, measured**: hand each one a
   `SkillContext` whose observation carries a single `GumpView` and `_bank_`, `_buy_`,
   `_craft_`, `_deliver_`, `_fetch_`, `_process_`, `_sell_` and `_toolbuy_can_yield` all go
   `True → False` (the bank's arrives indirectly, `_bank_idle` → `_bank_ui_clear`).
   `deadline_can_expire` is `not achieved and can_yield`, so **one unowned gump — the
   forge15 wedge, already in this document — holds bound 2 open forever, and holds bound 1
   open too**, since the readiness gates share that clause. A safety interrupt does the
   same with no surface to blame at all: `Survive`/`WarriorSurvive` sits above the
   capability skills in the CAPABILITY planner too, so a wounded character's economy agent
   is TICKED every tick while its FSM is never STEPPED.
3. **So overdue releases the hold.** `frame_overdue` — the frame is past its own
   `deadline_tick` on the economy agent's clock — drops the hold, and the Life becomes
   exactly the pre-fix Life: a stale frame, but alive and hunting. The release depends only
   on the frame's deadline and the economy counter, both of which the hold itself keeps
   advancing, and never on the FSM being stepped — which is precisely what those two states
   withhold. Worst case is now the frame's own budget in orchestrator ticks, and the
   registry's whole spread is small: `bank_gold` **120**, every buy / sell / fetch /
   deliver / process / upgrade **180**, the five `craft_*` **300**. So no hold can outlive
   300 orchestrator ticks plus the repair's slack — measured worst case over 1000
   randomized worlds, 270.

One extension, capped: an overdue frame first gets `_clear_stale_ui` POINTED AT IT
(`_repair_overdue_frame`). That repair's no-goal precondition exists because "a
mid-transaction gump belongs to a live goal" — a frame that has burned its ENTIRE budget
without once reaching a safe yield point has forfeited that premise, and the open surface
is the documented reason it can neither give up nor expire. When a close lands the hold is
extended one tick so the economy agent can USE it; capped at `OVERDUE_REPAIRS = 3` per
frame (one per closable surface class), so repair-and-extend cannot itself run away.
`frame_overdue` is computed from the frame and the clock ALONE, never gated on the hold —
gating it was review-caught blinding the report in exactly the half of the wedge where the
rule still happened to want the capability, and what the rule wants has nothing to do with
why the frame cannot finish.

**Death is the other override, and it covers the whole EPISODE.** `RecoverDeath` is a

  `craft_tongs` at 292/300 (4 tongs of a batch of 5, so unachieved) and `buy_iron` at
  177/180 (`iron=1`, so unachieved) both vanished from the next sample. Neither family
  writes `cap_run_finished_goal_id` and neither frame was achieved, so
  `CapabilityGoalComplete` had neither branch available: `expire_due` is the only thing
  that could have closed either. They rode their FULL budgets and retired on the deadline.
- **Bound 1 (the FSM give-up ladder) is UNEXERCISED as far as these logs can tell.** The
  original claim here was *"Bound 1 worked, and only where it exists — `sell_tongs` frames
  peaked at age 4 and `bank_gold` at 11, the two capability families that write
  `cap_run_finished_goal_id`."* That does not follow. All **eight** sampled `sell_tongs`
  frames in the 1800-tick run sit beside a COMPLETED sale — `tongs` → 0 and the tinker's
  gold up by the vendor's price on the adjacent sample, every time — and all **six**
  `bank_gold` frames beside a COMPLETED deposit (`banked` 0 → 23 → 118 → 223 → 328 → 433 →
  503, one per frame) — and `CapabilityGoalComplete.can_run` closes exactly that case by its
  ACHIEVEMENT branch (`profession.py:299`), before it ever reaches the run-finished branch
  at `:311`. The status line shows only that the frame is gone; it cannot name the branch.
  The control is in the same log: a **ladderless** `buy_iron` frame was last seen at age 4
  and gone by the next sample, exactly like `sell_tongs`. **A low max age is therefore not
  a give-up-ladder signature at all**, and nothing in these runs distinguishes bound 1 from
  ordinary success. Proving it live needs a transaction that FAILS — a sale the vendor
  refuses, a bank trip that cannot reach its banker — not another healthy run.
- **Bound 3 never fired, and the mechanism is narrower than first written.** `expire_due`
  triggers at `ticks >= deadline_tick` (`agent.py:638`) while `frame_overdue` needs
  `ticks > deadline_tick` (`warrior_life.py:535`), so a frame that CAN yield always retires
  one tick before the marker could print — that part stands. What was WRONG was the
  yield-point half: the original text said *"a terminal trip can yield even with a surface
  open: `_buy_can_yield` ends `(ui_clear or finished)` and `_craft_can_yield` ends
  `(not started or terminal)`."* Only the buy half is right. `(not started or terminal)` is
  `_craft_can_yield`'s SECOND clause (`capabilities.py:648`); the function goes on to
  require `obs.pending_target is None and not obs.gumps and obs.popup is None and
  obs.shop_buy is None and obs.shop_sell is None` (`:654-658`). **A terminal CRAFT trip
  cannot yield with a surface open — craft is precisely the family where a surface at the
  deadline WOULD produce an overdue frame.** The three frames that expired with `ui=shopbuy`
  still open were `buy_iron` frames, and `(ui_clear or finished)` is what let them; the
  292/300 `craft_tongs` frame expired because its sample carried **no `ui=` field at all**,
  so it was terminal AND clear. The conclusion survives — bound 3 did not fire — but by that
  route, not by "terminal is enough".
- **Which means bound 3 is closer to an ordinary run than this section first implied.**
  The blocking surface for a craft frame does not have to be UNOWNED: `not obs.gumps` is
  unconditional, so the craft FSM's own menu blocks its own yield point. These runs had **14
  `ui=gump` samples, every one of them on `craft_tongs`** — the state exists live; it simply
  never coincided with a deadline, because all 14 sat at ages 2–23 against a 300-tick budget.
  An ordinary run whose craft gump happens to be up at tick 300 reaches bound 3 by accident.
- **So `frame_overdue`'s release and `_repair_overdue_frame` have zero live ticks** — the
  exact component whose absence made the FIRST version of this fix livelock the wedged world
  (§5's first refutation, which measured **four of the five Lives pinned in economy mode with
  `hunt_after = 0` for the whole 3000-tick window**; the "24 of 24 worlds" that stood in this
  sentence is unsourced and is corrected in §5's CORRECTION note). Four tests and
  128-of-600 randomized worlds stand behind it, and nothing else.
- **Checklist item 5 was not exercised either:** nobody died in any of the three runs, so
  the death override and the corpse run remain offline-only too.
- **And `!frozen`'s zero is ENTAILED by the two absences above, not independent of them.**
  `life_runner.py:210-215` prints `!frozen` only when a frame is live AND
  `getattr(life, "mode", "economy") != "economy"` (`:212-213`). But `tick`
  (`warrior_life.py:533-541`)
  sets `holding = (mode != "economy" and frame is not None and not
  self._death_episode_open(obs) and (not self.frame_overdue or repaired))` and then forces
  `mode = "economy"` whenever `holding`. So with a frame live, the mode can only be
  non-economy if a death episode is open or the frame is overdue-and-unrepaired — and this
  section has just recorded that NEITHER occurred. `!frozen = 0` was structurally
  unreachable on these runs. It belongs with the things the runs could not test, not with
  the things they proved.

**What a future run should do to reach bound 3 — do not wait for one to happen.** Follow
this document's own method (forced-state gates find FSM bugs) with a `live_*_gate.py` in the
shape of `live_tinker_bank_gate.py`: stage the tinker mid-`craft_tongs`, have the CONTROL
plane put a surface the brain does not own in front of it *while the frame is still
running* (a GM-opened gump is the one with no FSM-level owner — a vendor BUY window is not,
per `8cdd2f0`), and run past the 300-tick craft budget. Assert three things: `FRAME
OVERDUE` prints, `closing an unowned …` prints just before it, and the status tag returns
to `[hunt]` within the frame's own budget. A wounded-character variant (`Survive` starving
the FSM with no surface at all) exercises the release path that cannot depend on the
repair. Both are minutes of live budget, not hours. **A cheaper variant now that the
mechanism is read correctly:** hold the craft menu open past the craft budget — no GM gump
needed, since `_craft_can_yield` refuses on any gump — which the same gate can do by
stalling the FSM's own close step.

#### 6.4 The 292-tick hold, read closely

One `craft_tongs` frame ran from age 8 to 292 — 32 of the run's samples, 31 of them marked
`+hold`, which is every `+hold` in the run. What it actually was:

- **The clock MOVED the whole way**: ages 17, 26, 35, 45, … 292 against Pim's own tick
  counter 402, 411, 420, 430, … — exactly 1:1, because the hold keeps the economy agent
  being ticked. This is the precise opposite of §3's defect, where the age would have been
  pinned. It is not a freeze.
- **The world was static** — precisely: Pim's position `(2608,475)` and `steps=198` are
  unchanged on all 32 samples, and `iron=0 tongs=4 gold=72 banked=23 net=+95g` holds for
  **30 of the 32**. *(This bullet first said the whole line was "unchanged for the entire
  window". It was not: at age 8 the pack read `iron=4 tongs=1` and at age 17 `iron=2
  tongs=2` — the last two crafts of the batch, finishing as the iron ran out. From age 26
  to 292 nothing moves. Gold, banked and net are constant across all 32.)* The tinker was
  waiting on
  the miner — `drop[grimm_sees=0 pim_sees=0]` throughout — and the delivery landed ~75 ticks
  AFTER the frame retired: the miner's reward jumped 107.8 → 176.8 as it reached the drop at
  `(2609,475)`, and the tinker's `iron` went 0 → 69 on the next sample (the drop counters
  stay 0 on both sides because the pickup fits inside one ~9-tick sampling interval).
- **It was terminal-but-unachieved, and that is the finding.** `cap_craft_stage=finished`
  from age 26 on, with `tongs=4`. `TinkerTongs.craft_batch` is 5 (inherited), and the craft
  proof ends `_pack_graphic(ctx, output_graphic) == batch` — so 4 tongs is NOT achieved.
  Craft writes no `cap_run_finished_goal_id`, so `CapabilityGoalComplete.can_run` had
  neither of its two branches. The frame had no exit but its deadline and took it: last
  seen at 292/300, gone by the next sample, no `!overdue`.
- **So the honest label is neither "freeze" nor "slow close": it is bound 2 doing the
  ENTIRE job on a capability family that has no bound 1** — §5's own paragraph 1, live. The
  surrounding `craft_tongs` frames, last seen at ages 17–28, are the ones where the batch
  completed and the achievement proof closed them.
- **The cost was real, and it was not work.** `want=None` for the whole window: iron 0
  (nothing to craft), 4 tongs (below the sell line), 72 gold. The tinker's `work_skill` is
  `None`, so its hunt mode is wandering — the ~275 ticks between the first and last `+hold`
  sample displaced wandering, not production. Pre-fix, those same ticks would have been
  wandering beside a frame frozen at
  age 17, which is the state §3 recorded and which refuses every new proposal — and the
  miner's 69 ingots arrived while that frozen frame would still have been there.
- **What it argues for** is giving the ladderless families a neutral run-finished marker so
  a terminal-but-unachieved craft closes on the tick it becomes terminal instead of 266
  ticks later. Follow-up 15.

#### 6.7 What the runs found that is NOT the hold: the vendor BUY window did not clear

The stale-UI section above (2026-07-31) says the "each recurrence costs one goal lifetime"
gap is CLOSED by commit `8cdd2f0`, with the honest half that the FSM-layer half of that fix
had OFFLINE TESTS ONLY and live re-verification outstanding. **These runs are that
outstanding re-verification, and the cost that gap was supposed to close is back.**

- 1800-tick run, from the tinker's t≈1244 to the end: `ui=shopbuy` on **75 consecutive
  samples** (36% of the run's samples), iron stuck at 1, and **three complete `buy_iron`
  frames each riding its FULL 180-tick budget** (ages 6→177, 5→176, 4→176) before expiring.
  Each expiry was followed ~10 ticks later by the repair and the alarm (§6.6), and the
  surface was present again on the very next sample. That is the "one goal lifetime per
  recurrence" shape, three times over.
- **The window was the FIRST trip's own, not a stranger's.** The sample before it
  (`bank(stage=deposit …)`) carries no `ui=` field at all, and the next reads
  `buy_iron(mkt_phase=buy … buy_stage=popup)` with `ui=shopbuy` — the trip opened it, then
  ended at `mkt_phase=craft` with the window still up, `buy_stage` popped and no iron
  bought. That is forge16's shape ("a vendor BUY window left behind by a finished
  `buy_iron` trip"), not `8cdd2f0`'s ("a window already open when a trip starts"), so this
  run gave the FSM-layer fix no observed opportunity to fire: it is still untested live,
  and it is not what failed here.
- **But `8cdd2f0`'s own case DID occur on trips 2 and 3 — it just never reached the stage
  where its fix lives.** Correcting the bullet above, which is right about the FIRST trip
  and was over-generalized in follow-up 16 to "that case never arose": the second wedged
  `buy_iron` frame opens at `@5/180` on a sample whose PREDECESSOR already reads
  `ui=shopbuy` (`want=buy_iron admitted=None … ui=shopbuy`), and the third does the same at
  `@4/180`. Both therefore START against a window that is already open — exactly
  `8cdd2f0`'s premise. What neither of them does is reach the buy FSM's **popup stage**,
  which is where the empty-list cancel is emitted: every one of their samples reads
  `mkt_phase=craft` with `buy_stage` ABSENT, whereas the first trip's opening sample read
  `mkt_phase=buy … buy_stage=popup`. So the honest statement is **no OBSERVED OPPORTUNITY
  to fire**, not "the case never arose" — and that sharpens candidate (b) below from a
  guess into the leading one.
- 600-tick run: the same shape, just starting. Its last 7 samples are `buy_iron` 5→55/180
  with `ui=shopbuy` and gold 82 / banked 188 frozen. **It did not "end healthy, the run
  ended not the agent"** — it ended in the opening of this wedge.
- **Nor did the 1800-tick run end healthy.** It ended with the tinker's budget spent, its
  third wedged `buy_iron` frame just expired, `want=buy_iron admitted=None ready=[]
  ui=shopbuy`, and `NO PROGRESS for 560 ticks`. The last 12 samples show only the miner
  still ticking — *and "ticking" is all he is doing: he had produced nothing since t=765,
  §6.5. Neither agent was healthy at the end of this run.*
- **The mechanism is not resolved by these logs and is not guessed at here.** Two candidates,
  both cheap to falsify offline: (a) the empty-list cancel is emitted but the surface is not
  actually closed — server-side, or because the body's observation keeps a stale `shop_buy`;
  (b) the follow-on trips never re-enter their buy phase at all — every wedged sample reads
  `mkt_phase=craft` with `buy_stage` ABSENT (i.e. popped), which is what a trip that already
  finished for a previous goal id looks like, not one at its popup stage. Follow-up 16.
- One thing this DOES confirm of §5: the shopbuy rows RELEASE. Every one of the three frames
  retired on its own deadline and the Life was never pinned. The livelock §5's first
  refutation measured needs a surface with no FSM-level owner, and this is not one.
