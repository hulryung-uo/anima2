# Multi-team audit — 2026-07-29

Six review teams (architecture, roadmap, process, tests, economy, devil's-advocate) were
run against this repo, their top proposals adversarially verified (three were refuted or
corrected — including one fabricated roadmap citation the verify pass caught), then
synthesized. The devil's-advocate team was lost to an infrastructure error; the synthesis
rests on the other five. This document records the FINDINGS; none of the proposals below
are decisions until acted on.

## Verdict

Micro-level engineering is genuinely strong: differential live gates with honest verdicts
(losses and retractions reported as-is), provenance-wiped economics, a fail-closed
capability authority boundary, 1327 tests in under 4 seconds. What is not going well is
structural: the project keeps paying for ONE defect class — a single world-fact defined in
two places (decide rule vs capability gate; runner N vs runner N+1) synchronized only by
memory. Six live failures trace to it, and **the audit found a seventh, latent today**:
`mage_life.py`'s `fetch_gold` rule ignores the `PICKUP_RADIUS` and pack-cap its gate
enforces (the carpenter's fix was never back-ported). Meanwhile the flagship "Lives" run
on scripted cognition (`_LifeClient` echoes `decide_mode`'s choice as fake LLM JSON) with
no Phase-6 persistence wired in — so the AI-native showcase is currently a hand-written
FSM village whose live hours accumulate no society state — and both deployed craft loops
destroy value at vendor prices (throne −33g; dagger batch −25g once staged iron runs out;
an Ettin pays ~157g vs +10g for the best craft trip).

## Top risks

1. **The dominant failure class does not converge under the current process** — six
   incidents fixed one at a time; the seventh (mage fetch_gold) already exists.
2. **Lives bypass the LLM brain and Phase-6 persistence** — the differentiators sit idle
   while deterministic rules do everything.
3. **Craft loops are value-destroying by construction** — a society scaled on them decays
   to bankruptcy, and gold-per-life fitness would rank crafters below doing nothing.
4. **Resumability contract broken** — CLAUDE.md's "Next:" (~90 commits stale) contradicts
   AUTONOMY-ROADMAP.md §E; this session's live proofs live in uncommitted scratchpad
   scripts.
5. **Scaling cliff at ~3–4 concurrent agents** — hand-tuned pump budgets, insertion-order
   capability priority, string-key contracts across two memories per agent.

## Proposal 5 was WIRELESS — and proposal 1's defect class was still live (2026-08-02)

Two re-examinations of already-"done" work, both of which found the mechanism present and
the wiring absent. The pattern is worth naming on its own: **a proposal implemented at the
callee and never at the caller reads as landed from every angle except the one that
matters.** The implementation record above marks both #1 and #5 complete, honestly — the
code each describes does exist. **The gap is a different one for each, and an earlier
draft of this paragraph flattened them into "neither could be USED", which is false of #1
and contradicted by this document's own record of it:**

- **#5's channel could not be used at all.** No production site could pass a threshold, so
  nothing outside the tests ever did (details below).
- **#1's suite could be used, was used, and earned its keep** — implementation record #1
  above: it failed on the latent mage drift on its first run and later caught a genuinely
  dead `bank_gold` branch in a brand-new `TinkerLife` before that Life's first live run.
  Its defect is narrower and it is coverage: the suite was BLIND along three whole axes at
  once — every fixture injected a backpack, every knob was pinned at its module default
  (where rule and gate agree by construction), and both craft lattices pinned `craft_spot`
  to the player's own tile. Four distinct rule-vs-gate disagreement classes were sitting
  inside those blind spots — the three pack-absent fetches recorded below and the
  carpenter's craft, whose batch clause is reachable on a shipped runner today. A suite
  that runs and passes is not the same as a suite that looks.

**Proposal 5 ("Life thresholds → constructor parameters").** The record says
"`bank_reserve`/`econ_grace` params". True — and `LifeSpec.life_factory` was typed
`(body, persona, routes) -> Life`, `LifeRunner.run` called it with exactly those three
positional arguments, and both shipped factories in `village.py` were
`lambda body, persona, routes: ...`, which would have raised `TypeError` on any keyword. So
no production site could pass a threshold and none ever did — only tests, by constructing a
Life directly. The prerequisite the proposal existed to create ("for genome axes, bandit
tuning, and slow-loop steering to touch them") was therefore never created, and CLAUDE.md's
deferral precondition (a) was nominally satisfied by it. What closed the gap:

- `LifeSpec.knobs` (a dict forwarded as keyword arguments) and `LifeRunner.build_life()` —
  a NAMED seam, because `run()` needs a live shard, so a knob channel proved only by
  re-implementing that one line in a test is a channel asserted but not wired. Offline
  tests and the live path now call the same method.
- Both `village.py` `LifeSpec` factories take and forward `**knobs` — and, as of the same
  day, both `LifeSpec` RUNNERS grew the caller-side end of it:
  `run_carpenter_life(knobs=...)` / `run_woodsman_life(knobs=...)` pass
  `LifeSpec(knobs=dict(knobs or {}))`. Copied, not aliased: a sweep script that reuses one
  dict must not be able to retune a Life that is already built. Default `None` keeps every
  existing caller byte-identical. Five of the seven construction sites still have no entry
  point — follow-up 2.
- `anima2/knobs.py` — the ONE clamped read: `knob_int(memory, key, default)` for a knob a
  `decide` staticmethod must see (it can only see memory), `knob_param(value, default)` for
  one only `tick()` reads, `type(value) is int` so a `True` clamps instead of passing as 1.
  `skills/market.py::_bank_reserve` (name, signature, docstring intact) is now that read
  bound to its key. This generalizes the lesson the natural-deposit campaign paid for above
  — "the bank_reserve raw-vs-clamped read that recreated the rule-vs-gate drift class
  through the tuning knob itself" — so knob N+1 inherits it without anybody remembering.
- Two new knobs (`WarriorLife(disagreement_ticks=...)`, floor 1 because floor 0 makes
  `streak >= window` true every tick and a HEALTHY Life would then self-report and fire

### 5. The fix — an exit-edge hold, and the third bound the review had to put on it

**Follow-up 10 is closed. OFFLINE ONLY WHEN THIS WAS WRITTEN — read "The honest half"

weakened or deleted**, both ruff gates clean. `docs/WOODSMAN.md` carries the operator

*The pre-existing hole, worth its own sentence because the new report would have shipped
dead through it:* `_ThrottledAgent` (the proxy `run_supply_pair` and
`run_artisan_mage_village` drive their Lives through) has no `__getattr__`, so
`_run_worker`'s `getattr(agent, "rule_gate_disagreement", None)` was unconditionally
`None` for the throttled carpenter and the throttled mage — **the two Lives that run their
economy agent nearly every tick were the two that could never print the disagreement
alarm.** Both self-reports now pass through explicitly.

**The mechanism, restated in one paragraph.** `decide_mode` is a pure function of
`(obs, memory)` — that purity is the property the ~150k-point concordance lattice rests
on — so it structurally cannot see the goal stack, and it answers `"hunt"` the instant the
world-fact its branch was keyed on flips. For every economy branch of all five Lives that
fact is something the transaction ITSELF changes: the goods leave the pack, the coin
moves, the pile is lifted. For a sale that instant is the moment the vendor TAKES the item
— mid-transaction, with the walk home still owed. `WarriorLife.tick` then ticks the OTHER
agent, and three things freeze together because all three only advance inside
`Agent.tick`: the capability FSM, the `cap_*_finished` markers it would have to write
(every capability `step` returns `RUNNING`, and `CapabilityGoalComplete` is a planner
skill selected on a LATER tick), and `GoalStack.expire_due`, whose deadline is counted in
that same agent's ticks. §3 above has the live numbers.

**What the fix does.** `WarriorLife.tick` gains an EXIT-edge rule, after the `econ_grace`
entry hysteresis and before `self.mode` is assigned: if `decide` answered `"hunt"` while a
frame is live on the economy stack, the mode is HELD at `"economy"` so the frame's owner
agent keeps being ticked and can finish what it started. Three deliberate non-changes ride
with it: **`decide_mode` is not touched** (all five stay pure, so the concordance lattice
and its `_NOT_DRIVEN_BY_THE_LIFE` equality are untouched); **`want=` is not rewritten** to
the held frame's capability, because fixing the `admitted=` lie by rewriting `want=` would
re-create the identical ambiguity on the other side; and **one agent per orchestrator tick
stays the rule** — follow-up 10's candidate (i), a second economy tick on the exit edge, is
exactly what was NOT done, since that is what would make "which agent ticks" conditional on
goal state and break the route/reflex cadence the extra-pump comment records. The one
addition is a pin: `_econ_streak` is held at `econ_grace` for the duration, so the tick a
transaction retires commits straight back to the economy instead of re-earning a
hysteresis that exists to filter a mid-equip transient, not a completed trade.

**The bound, and why it needed a third one.** The first implementation claimed the hold
was self-limiting on two bounds. It is not, and the review measured why:

1. **The FSM's give-up ladder** returns `mkt_phase` to `"craft"` and writes
   `cap_run_finished_goal_id`, which `CapabilityGoalComplete` closes as a FAILURE. This is
   the usual exit and it is the forge1/forge13 lifecycle fix doing its job — but
   `grep -rn cap_run_finished_goal_id anima2/` has exactly **two writers**,
   `skills/market.py:1529` (`SellItemCapability`) and `:1920` (`BankGoldCapability`).
   Every buy / tool-buy / craft / fetch / process / deliver frame has no ladder at all.
2. **The frame's own deadline**, via `GoalStack.expire_due` — reachable only because the
   hold keeps the economy agent ticking. But `CapabilityPolicy.deadline_can_expire` defers
   at an unsafe yield point, and every `*_can_yield` in `capabilities.py` carries the same
   unconditional "idle UI" clause — **all EIGHT of them, measured**: hand each one a
   `SkillContext` whose observation carries a single `GumpView` and `_bank_`, `_buy_`,
   `_craft_`, `_deliver_`, `_fetch_`, `_process_`, `_sell_` and `_toolbuy_can_yield` all go
   `True → False` (the bank's arrives indirectly, `_bank_idle` → `_bank_ui_clear`).
   `deadline_can_expire` is `not achieved and can_yield`, so **one unowned gump — the
   forge15 wedge, already in this document — holds bound 2 open forever, and holds bound 1
   open too**, since the readiness gates share that clause. A safety interrupt does the
   same with no surface to blame at all: `Survive`/`WarriorSurvive` sits above the
   capability skills in the CAPABILITY planner too, so a wounded character's economy agent
   is TICKED every tick while its FSM is never STEPPED.
3. **So overdue releases the hold.** `frame_overdue` — the frame is past its own
   `deadline_tick` on the economy agent's clock — drops the hold, and the Life becomes
   exactly the pre-fix Life: a stale frame, but alive and hunting. The release depends only
   on the frame's deadline and the economy counter, both of which the hold itself keeps
   advancing, and never on the FSM being stepped — which is precisely what those two states
   withhold. Worst case is now the frame's own budget in orchestrator ticks, and the
   registry's whole spread is small: `bank_gold` **120**, every buy / sell / fetch /
   deliver / process / upgrade **180**, the five `craft_*` **300**. So no hold can outlive
   300 orchestrator ticks plus the repair's slack — measured worst case over 1000
   randomized worlds, 270.

One extension, capped: an overdue frame first gets `_clear_stale_ui` POINTED AT IT
(`_repair_overdue_frame`). That repair's no-goal precondition exists because "a
mid-transaction gump belongs to a live goal" — a frame that has burned its ENTIRE budget
without once reaching a safe yield point has forfeited that premise, and the open surface
is the documented reason it can neither give up nor expire. When a close lands the hold is
extended one tick so the economy agent can USE it; capped at `OVERDUE_REPAIRS = 3` per
frame (one per closable surface class), so repair-and-extend cannot itself run away.
`frame_overdue` is computed from the frame and the clock ALONE, never gated on the hold —
gating it was review-caught blinding the report in exactly the half of the wedge where the
rule still happened to want the capability, and what the rule wants has nothing to do with
why the frame cannot finish.

that is the only agent that ever owns a death episode. The frame simply WAITS while the
episode runs (telemetry says `!frozen`), and the hold resumes when it closes.

### 8.1 Follow-up 17 — the liveness line, adopted at the SECOND time of asking

**The plainest thing to say about this fix is that it should have existed before the run that
needed it.** The 2026-07-30 post-implementation health check ends: *"Also worth adopting from
the same report: a liveness line for NON-Life agents (the forge miner died silently —

**What the old alarm could not do, measured on the 1800-tick log.** `NO PROGRESS` is
BODY-liveness: reward, steps, speech AND position, so an agent that keeps WALKING resets it
forever. Grimm kept relocating. His ten `NO PROGRESS` pulses land at ticks
`38, 95, 291, 798, 872, 1078, 1325, 1577, 1800, 1800` and every one of them reads the

Identical text in the healthy half and the dead half is zero information.

**The signal that works, and what arms it.** `village._work_recorded(agent)` — the agent's own

variety, so a miner productively swinging one skill for 3000 ticks bumps it thousands of

### 8.2 Follow-up 16 — the wedge: fixed offline, and the mechanism named

§6.7 lists two falsifiable candidates for why a re-entering `buy_iron` trip never reaches its
own popup stage and refuses to guess between them. Offline reproduction found **three**
defects, not one, and they compose into exactly the shape the log shows. All three are fixed in
`anima2/skills/market.py`, mirrored to the tool-buy FSM (same machine, different memory
namespace, so it had the same defects and gets the same fixes rather than waiting to be caught
on its own run).

**(a) `buy_offer_reopens` outlived its trip — this is candidate (b), sharpened.** The counter
that decides how fast the partial-subset re-roll gives up was written and read in `_buy_step`
and **nowhere else in the repo**: not in `_CLEANUP_KEYS`, not in `_begin_goal`'s pop list, not
in the live gate's transaction keys. It therefore lived in the economy agent's memory for the
life of the process, and one unlucky trip that exhausted it left **every later trip giving up
on its first `window` tick, forever**. Measured offline on the FSM alone: trip 1 gives up at
tick 7 with the counter at `OFFER_REOPEN_ATTEMPTS`; trips 2 and 3, fresh goal ids and the same
memory, give up on tick 1. Fix: both counters added to `_CLEANUP_KEYS`.

**(b) The "re-roll" re-rolled nothing.** On an unlucky window the FSM flipped its stage back to
`popup` and emitted **no action**. A vendor window is a SNAPSHOT, so the subset cannot change
while it stays open — and `8cdd2f0`'s entry-edge branch at the popup stage then recognises the
still-open window as ours and flips straight back to `window`, re-reading the identical entry
list. Four attempts burnt in about four ticks. Fix: the re-roll emits
`BuyItems(vendor=…, items=[])`, ServUO's EndVendorBuy, so the next opening is a freshly rolled
subset.

**(c) No give-up path closed the window the trip had opened — the EXIT edge.** Seven
`return None` give-ups in `_buy_step` and not one cancelled the window, so the trip walked home
leaving a `ui=shopbuy` that refuses all sixteen capability gates (they share the idle-UI
clause). `8cdd2f0` fixed the ENTRY edge and §6.7 measured it working as designed; it never
touched this one. Fix: `BlacksmithMarket._close_own_vendor_window`, called on the give-up
transition of both buy capabilities.

**The safety argument for (c) is in the helper's own docstring, and it is the argument this
area exists to make.** It is **not a repair**: it is the OWNER cleaning up, emitted from inside
the trip's own FSM on the tick that FSM has itself decided the trip is over, so no other goal's
transaction can be in flight behind it. It closes ONE surface and only if `obs.shop_buy.vendor`
equals the serial **this trip** recorded (read BEFORE `_CLEANUP_KEYS` pops it); a stranger's

### 9.4 The obvious implementation is wrong, and it was measured rather than reasoned about

`Agent.tick` has maintained `memory["death_episode"]` — a monotone count of alive→dead edges
— since the recovery work, and nothing reads it for telemetry. Reading it is the one-line
version of this change.

It does not work for a **Life**, which owns two `Agent`s with separate memories and ticks
exactly one per orchestrator tick, each keeping its own `death_observed_dead` flag. Both
reductions were run on a real `CarpenterLife` over `MockBody`:

| staged | hunt marker | econ marker | `sum` | `max` |
|---|---|---|---|---|
| ONE death, seen by the economy agent, then by the hunt agent under the death override | 1 | 1 | **2** ✗ | 1 ✓ |
| TWO deaths, each seen by one agent only | 1 | 1 | 2 ✓ | **1** ✗ |

A sum double-counts and a max under-counts, so neither is a death counter. One body has one
death; the one worker watching that body counts it once. This is `_work_recorded`'s lesson
— a Life's telemetry cannot be read off one of its two ledgers — reaching the OPPOSITE
conclusion, because episodes genuinely add across the two agents and deaths do not.

Both reductions are pinned as mutants: implemented against this tree, each fails **4 of the
18** tests in `tests/test_forge_relocation.py`, and each fails on the assertion written for
it — the `sum` mutant prints `deaths=2` where the one-death fixture demands `deaths=1`, the
`max` mutant prints `deaths=1` where the two-death fixture demands `deaths=2`. Both fixtures
are one worker run over a real `CarpenterLife`, so neither mutant can be rescued by summing
across workers instead.

### 10.1 What was actually missing, and it was not the argument

Adding `knobs=` to four runner signatures is the easy part and it is not what follow-up 2
warned about. Its stated hazard was *"threading a dict through hand-written construction
per runner (no single point that stays true)"* — five independent copies of a check whose
whole value is that everyone performs it identically. So the change is three shared things
and four thin call sites:

- **`life_runner.validate_knobs(knobs, knob_names, *, label)`** — the check and its refusal
  text, lifted out of `LifeSpec.__post_init__`, which now delegates. One definition of
  "is this a knob" for the spec path and the inline path both.
- **`life_runner.build_tuned_life(life_cls, knobs, /, **kwargs)`** — `LifeRunner.build_life`
  for the runners that have no spec, and it exists for the reason that one's docstring
  already gives: those runners need a shard, so without a named seam the only way to prove
  a tuned value reaches the Life is to re-implement the construction line inside a test,
  which is the exact shape of an asserted-but-not-wired channel. It reads `life_cls.KNOBS`
  off the class, so unlike `LifeSpec` (whose factory is a lambda and must be TOLD its
  allowlist via `knob_names`) no site can declare the wrong one.
- **`village._route_knobs`** — the CLI's role routing, replacing the blanket
  `--knob needs --carpenter or --woodsman` guard, which was an allowlist of the two wired
  runners rather than a property.

### 10.2 The placement is the part a shared helper cannot choose for you

`LifeSpec` checks at spec construction and gets "before the first packet" for free. An
inline runner builds its Lives only after the logins, the GM staging, the provenance
gold-wipe and the seed grant — so each one calls `validate_knobs` at the TOP of the
function, above `ResilientIpcBody.spawn`, and `build_tuned_life` checks again at the point
of use. Same check, run twice, deliberately.

**Mutation-tested, and the mutant is worse than expected.** Removing `run_forge_pair`'s
pre-flight call — leaving only `build_tuned_life`'s check, i.e. checking at construction —
does not merely move a traceback later. The runner's login loop catches per-role

Two spawned accounts, and a message blaming the shard for a typo in an argument. The test

## 11. Follow-up 4 — the knob that rode a second channel, and §E's first real axis (2026-08-05)

Follow-up 4, verbatim: *"`wander_leash` is the cheapest remaining axis (§E's 'exploration
radius') and needs no Life work — but it arrives through `Staged.leash`, a DIFFERENT
channel, and `skills/movement.py::Wander._homeward` clamps it its own way (a malformed
value falls back to the class default rather than to a floor). Unifying the two is small;
noting the divergence matters more."*

`knobs.py` carried the carve-out in its own opening paragraph — a single-source module
whose docstring had to name the thing that was not single-source.

### 11.1 Which way the unification went, and why the other way was wrong

Two rules were in play for a present-but-malformed write:

| | `wander_leash=-1` | `=0` | `=1` | `=2` |
|---|---|---|---|---|
| class-default fallback (before) | **8** | 0 | 1 | 2 |
| floor clamp (now, `LEASH_FLOOR=1`) | 1 | 1 | 1 | 2 |

The fallback is **discontinuous**, and that is disqualifying for a knob whose entire
purpose is to be SEARCHED: a mutation stepping one below the floor leaps the behaviour to
the shipped default instead of resting on the boundary. Every other knob is monotone at
its floor, and a monotone boundary is what makes an axis searchable at all. So `_homeward`
now reads `skills/movement.py::wander_leash(memory, default)` — the key's one read point,
delegating to `knob_int`, in `market._bank_reserve`'s shape.

**The floor is 1, not `knob_int`'s natural 0, for `disagreement_ticks`' reason:** 0 is
catastrophic for THIS threshold. The only tile inside a 0-leash is `wander_home` itself,
so a leashed agent steers home on every tick it is not standing on it and never wanders —
the skill disabled by a malformed write rather than tuned by it.

**One stated behaviour change:** a stored `0` used to be honoured as a zero-tile leash and
now clamps to 1. No caller passes 0 — every production and gate call site passes >= 1.

### 11.2 The axis, and the precedence question it is the only knob to have

`wander_leash` is now in `WarriorLife.KNOBS`, so all five Lives take it and all seven
construction sites and all six Life-bearing runners carry it (§10). It travels as a MEMORY
KEY rather than an instance attribute, because `Wander` is a skill reading `ctx.memory` and
an attribute would be invisible to the only thing that uses it — the `bank_reserve` shape,
written raw and clamped by its reader.

**It is the only knob something else already writes**, and that makes it the only one with
a precedence question. Every runner calls `set_leash(home, derived)` AFTER construction:
`LifeRunner.run` with `staged.leash`, `run_supply_pair` with
`min(max(1, shop_reach), PICKUP_RADIUS - 1)` (live-caught, after Sten drifted three tiles
off his own supply drop and walked into a wall with `fetch_boards` correctly admitted the
whole time). Left alone, that later write would silently overwrite the tuned value — **a
channel that reports success and changes nothing, which is the exact defect §10 and the
2026-08-02 entry have been closing, wearing a knob that looks wired.**

So the TUNED value wins and `_leash_tuned` records the difference between "nobody set this"
and "a caller chose it". The derived value keeps exactly its old authority when untuned,
which matters because it is a live-caught fix. Mutation-tested: restoring the
unconditional write fails 2 tests.

The `home` is written unconditionally in both cases. It is not a knob and has no contest.

### 11.3 Three banners that would have started lying

A tuned leash is invisible unless the runner reports the EFFECTIVE value, and this is the
third time in three days that a banner has had to be moved off a local or a module
constant onto a read of the built Life:

- `LifeRunner.staged_line` gains `leash N` beside `reserve N`. It needs the read MORE than
  the reserve does, because with two writers neither input alone tells an operator what the
  Life will wander under.
- `run_supply_pair` printed its local `sten_leash`; it now prints what is in force and says
  `TUNED from a derived N` when they differ.
- `run_forge_pair`'s banner gains it alongside the reserve and the trip surplus.

### 11.4 What this does NOT establish

- **Offline only.** `127.0.0.1:2594` is down; no leash knob has been carried on a shard.
- **It is an axis nothing searches.** Same as §10.5: `Genome` still maps onto no knob, and
  `wander_leash` being §E's named "exploration radius" does not by itself connect the two —
  `Genome` has no leash field, and adding one is the genome→Life bridge that §10.5 says is

- **Untested live, and it CAN break a chain.** A leash above `PICKUP_RADIUS - 1` puts a

## 12. Follow-up 6 — three constants defined twice, merged (2026-08-07)

Follow-up 6 called these *"the audit's own headline defect class, in constant form"*, and
the framing is right: the concordance lattice catches a rule and a gate disagreeing about
a VALUE, and structurally cannot catch them disagreeing about a DEFINITION, because a
constant written twice is numerically locked until somebody edits one copy — and the edit
IS the failure.

### 12.1 The three, and they are not the same kind of problem

| pair | both sides read | could they diverge numerically? |
|---|---|---|
| `warrior_life.UPGRADE_RESERVE` ↔ `capabilities._UPGRADE_RESERVE` | `BuyArmor.tool_price_estimate` | **No** — same expression |
| `carpenter_life.BOARDS_PER_ITEM` ↔ `capabilities._FETCH_BOARDS_THRESHOLD` | `CarpenterCraft.craft_material_per_item` | **No** — same expression |
| `skills/survival.BANDAGE_GRAPHICS` ↔ `skills/warrior.BANDAGE_GRAPHIC` | a frozenset, and **the literal `0x0E21` typed again** | **Yes** |

The first two are one DECISION recorded twice — `_UPGRADE_RESERVE`'s comment in
`capabilities.py` was near word-for-word the one in `warrior_life.py`, and the fetch gate's
comment said it read the class attribute *"so it stays in lockstep with the craft gate that
consumes it"*, which is a property no comment can hold. Both now live in the skills layer,
which is the only place both readers can import from: `capabilities` importing a Life would
be a cycle, since the Lives import `CapabilityPolicy`.

### 12.2 The third pair had already produced a latent standoff

`BANDAGE_GRAPHIC = 0x0E21` sat three lines below `from .survival import BANDAGE_GRAPHICS`,
which is `frozenset({0x0E21})`. And the two were not decoration — they were **read by
opposite sides of the same decision**: `WarriorLife.decide` counted the SINGLE art while
`buy_bandage`'s gate counts `BuyBandage.buy_material_graphics`, the whole FAMILY.

Measured on one observation carrying 3 of the known art and 20 of a hypothetical second,
with the family grown to include it:

```
reorder line            : 10
pre-merge RULE counts   :  3  -> wants buy_bandage? True
GATE counts             : 23  -> admits buy_bandage?  False
merged RULE counts      : 23  -> wants buy_bandage? False
```

A permanent want-vs-refuse standoff, one added graphic away, in the exact shape the
concordance suite was built for — and invisible to that suite, because with a singleton
family the two sides agree at every lattice point. The rule reads the family now, so
the disagreement is not merely absent but unrepresentable: both names are bound to the
same frozenset object.

`BANDAGE_GRAPHIC` still exists, because a vendor OFFER is placed against one art and not a
family — a real distinction, not duplication. It is `min(BANDAGE_GRAPHICS)`, not
`next(iter(...))`: a frozenset has no order, so the iterator form would pick a different
graphic between runs the moment the family grew, and a buy offer that changes identity
between runs is the worst available failure here.

### 12.3 The tests are identity assertions, and they are mutation-checked

Equality would pass again the moment a second definition happened to compute the same
number, which is precisely the state being removed. So the three tests assert `is`, assert
the deleted private names are `hasattr`-absent, and — for the bandage pair — walk the AST
of `skills/warrior.py` to reject a bare literal, because `BANDAGE_GRAPHIC = 0x0E21`
satisfies an `in BANDAGE_GRAPHICS` check just as well as the derived form does.

Both mutants were implemented and both fail exactly one test: restating the bandage literal,
and reintroducing `capabilities._UPGRADE_RESERVE`.

- **Offline only, and nothing behavioural changed.** Every number is identical today; the

- **The standoff above is a CONSTRUCTED scenario, not an observed one.** No shard has ever

## 13. Follow-up 20 — the asymmetry, and why mirroring it would have been a regression (2026-08-07)

Follow-up 20: *"`8cdd2f0`'s entry-edge branch was never mirrored into `_toolbuy_step`. The
tool-buy popup stage still has no already-open-window handling ... a real asymmetry between
two copies of the same FSM, and it is unmeasured, so it was not guessed at."*

It was right to say unmeasured. Measuring it changed the fix.

### 13.1 The asymmetry was not one-sided

`_buy_step` had the entry-edge branch and `_toolbuy_step` did not, so the obvious reading is
"one FSM is missing a fix". The re-roll path says otherwise. After its own cancel,
`_toolbuy_step` had nothing to re-adopt the window with, so the popup stage simply waited and
re-requested — **each re-roll got a genuinely FRESH window**. `_buy_step`, with the branch,
re-adopts the window it just cancelled while the observation lag lasts, re-reads an identical
snapshot (a window IS a snapshot) and spends an attempt on it. That is the 4/2/1/1
fresh-openings-by-lag table already recorded in its own re-roll comment.

So each FSM had one half. Mirroring the branch alone would have taken the tool buy's good
half away — which is why follow-up 20's own conditional remedy (*"the fix, if one or two ever
proves too few, is a marker saying THIS trip just cancelled this window so the pre-check
refuses to re-adopt it"*) is not optional here. It is what stops the mirror being a
regression.

Measured by driving the REAL `_buy_step` / `_toolbuy_step` against a simulated shard whose
window never carries the item, counting FRESH window openings per trip (1 initial + up to
`OFFER_REOPEN_ATTEMPTS`=4 re-rolls, so 5 is the whole budget):

| lag (ticks) | 0 | 1 | 2 | 3 | 5 |
|---|---|---|---|---|---|
| entry-edge branch, no marker | 3 | 3 | 2 | 2 | 1 |
| shipped (branch + marker) | **5** | **5** | **5** | **5** | **5** |

Identical on both FSMs, which is the point. The lag costs ticks now (19/19/23/27/35 for the
same rows) and no attempts.

### 13.2 One method, not two copies

The stage is now `BlacksmithMarket._buy_popup_stage(ctx, ns, vendor_serial, reward)`, called
by both FSMs with their own memory namespace, returning `_ADOPT_WINDOW`, `None` (give the
trip up) or a `SkillResult`. Copying the branch would have produced a third thing to keep in
step; two copies of one FSM with one fix applied to one of them is this project's headline
defect class, and follow-up 20 is that class with the roles reversed from §12's.

### 13.3 An unbounded loop, found by moving one line

The `POPUP_TIMEOUT` count now runs ABOVE the window branch. It used to run below, and
`_buy_step`'s foreign-window branch returned its cancel before reaching it — so **a foreign
window that never closed produced a cancel every tick forever**, bounded only by the frame
deadline outside this FSM and never by the stage timeout that exists to bound it. Whether it
ever fired live is unknown: a stale window that outlives a full `POPUP_TIMEOUT` is exactly the
forge15-18 shape, but no log distinguishes "cancelled repeatedly" from "waiting". It is
bounded now, and the foreign window is cancelled ONCE and then waited on rather than
re-cancelled every tick.

### 13.4 Mutants

Both were implemented against this tree:

- **Mirror the branch WITHOUT the marker** — literally what follow-up 20 proposed. Fails 4
  tests, including the re-roll budget on BOTH namespaces.
- **Revert `_toolbuy_step` to its own popup stage** (the pre-merge asymmetry). Fails 3 tests,
  all on the `toolbuy` parametrization and none on `buy` — which is the asymmetry itself,
  visible as a test signature.

`{ns}_closing_window` went into `_CLEANUP_KEYS` in the same change that introduced it, with a
test pinning it, because `buy_offer_reopens` is in that tuple only because it was NOT and one
unlucky trip poisoned every later trip for the life of the process (§8.2).

### 13.5 The trade-off the marker buys, found by reviewing the change afterwards

`{ns}_popup_total` is cumulative across a trip (deliberately — it bounds the TOTAL time in
this stage across every re-request cycle) and it now counts the ticks spent waiting for a
cancel to land, which it did not before: those ticks used to be spent inside the `window`
stage, because the pre-check adopted the window instead of waiting. So the stage's own
timeout binds sooner. Swept against the same simulated shard:

| lag (ticks) | 1 | 2 | 3 | 5 | 8 | 10 | 12 | 15 | 20 | 30 |
|---|---|---|---|---|---|---|---|---|---|---|
| pre-change `_buy_step` (branch, no marker) | 3 | 2 | 2 | 1 | 1 | 1 | 1 | 1 | 1 | 1 |
| shipped | 5 | 5 | 5 | 5 | 5 | 5 | 4 | 3 | 3 | 2 |

At lag ≥ 12 the trip no longer spends its whole re-roll budget, and at ≥ 15 it ends on
`POPUP_TIMEOUT` rather than on the budget. **It is still better than what it replaced at
every lag measured**, so this is a smaller ideal, not a regression — and the realistic band
at `pump_ms=400` is 1-3 ticks (a 15-tick lag is six seconds for a window to close on a
loopback shard). Recorded because a future reader measuring only the shipped column at lag
15 would reasonably think something was broken.

Not "fixed" by exempting the wait from the counter: that exemption is exactly the unbounded
loop §13.3 removes.

### 13.6 What this does NOT establish

- **Offline only.** The shard is down; neither FSM has run a tuned or untuned trip on a
  shard since this change. The lag table is a simulation, not a live measurement — its lag
  parameter stands in for a real `pump_ms=400` round trip that nobody has instrumented.
- **The entry edge has still never been observed firing on the TOOL path.** `buy_tinker_tool`
  is a rare capability (a tool is bought when one is lost), so the window it would adopt is
  one some OTHER trip left behind. §8.2(c) made every trip close its own window on the way
  out, so the residual case is a trip that never got to run its give-up path at all — a frame
  expiring mid-trip, or a mode switch. That is a real shape (bound 2 fires; §6.3) but it has
  not been caught with a tool buy on the other side.
- **`OFFER_REOPEN_ATTEMPTS=4` is unchanged and unvalidated.** The marker means all four
  attempts now buy four distinct snapshots; whether four is the right number for the
  ~15-of-45-entry pairing bug is still the estimate it always was.
- **Nothing here touches follow-up 19**, the give-up marker that would let a buy frame retire
  through bound 1 instead of burning its deadline. Bound 1 remains unexercised live.

## 15. An independent review of §§9-14, and the five defects it found (2026-08-07)

§14 was a SELF-review and found three things. An independent pass over the same range
(`1d3381c..HEAD`, high effort) found five more, all real, all reproduced before being
fixed. That ratio is the entry's point: reading your own diff is worth doing and is not a
substitute.

### 15.1 The five

**1. `wander_leash` is clamped downward only, and it overrides leashes that are
correctness constraints rather than preferences.** `run_forge_pair` and `run_supply_pair`
both derive `min(max(1, shop_reach), PICKUP_RADIUS - 1)` so the agent stays inside pickup
range of its own ground drop — the live-caught defect Sten's leash exists to prevent. §11
made a tuned value outrank that, so `--knob wander_leash=40` lets Pim wander 40 tiles from
the forge and the flagship chain stops closing with no line saying why. §11.4 recorded the
hazard and called it correct-for-a-searched-axis; what it missed is that it is SILENT.

*Not fixed with a ceiling.* An "exploration radius" that cannot explore upward is not an
axis. `leash_readout(memory, life)` now names the override:
`40 (TUNED over a derived 5 — beyond the range this runner computed for reaching its own
drop; deliveries may go unfetched)`. `set_leash` remembers what it yielded to so the
banner can say it.

**2. `set_leash`'s new precedence applied to every call, not just the staging one.**
`live_frame_overdue_gate.py` teleports the tinker and re-leashes it to the new spot, with
a stated invariant — *"if `Survive` ever let go, `Wander` would walk the tinker back onto
its craft spot and the rule would want the economy again on its OWN account, silently
un-engaging the hold"*. Against a tuned Life that re-leash became a no-op and the gate
could report a bogus pass. Latent, not live: nothing tunes that gate today.

Fixed by splitting what the precedence is FOR. A runner's staging call passes a value
DERIVED from the world as a default and yields to tuning; a later call is a runtime
decision and wins. `_leash_tuned` is consumed by the first explicit leash.

**3. The foreign-window cancel was sent exactly once and never retried.** §13.3 replaced
an unbounded every-tick re-send with one cancel and a wait. A cancel is a packet and a
packet can be dropped — and on the give-up path `_close_own_vendor_window` *deliberately*
refuses a window belonging to another vendor, so nothing else would close it either. The
trip would end on `POPUP_TIMEOUT` leaving open the exact surface that refuses all sixteen
capability gates, which is forge15-18's own failure. The old code was unbounded but
self-healing; the new one was bounded but not. It is now both: re-sent on `_popup_click`'s
own `ASK_RETRY` cadence.

**4. The per-trip counters survive a frame torn down MID-trip.** `_CLEANUP_KEYS` is popped
when a trip ends NORMALLY — the step function returns `None` and the phase switches to the
walk home. A frame that expires on its deadline never reaches that line, and bound 2 makes
that a MEASURED shape rather than a hypothetical (§6.3 recorded `buy_iron` frames closing
exactly that way on a shard). So a spent `offer_reopens` made the next trip give up on its
first `window` tick, and a stale `closing_window` made its popup stage wait out
`POPUP_TIMEOUT` for a window nobody was closing. `buy_offer_reopens` had this exposure
already; §13's key inherited it.

Fixed in `_begin_goal` for the two buy families, **narrowly**: the three per-trip counters
only. The first attempt popped all of `_CLEANUP_KEYS` for all four families, which is more
correct in principle and broke six bank tests — those fixtures seed mid-FSM state without
`cap_bank_goal_id`, a state production cannot reach, so they were arguably wrong. It was
reverted anyway: clearing the STAGE keys is a wider behaviour change on the flagship path
that nothing offline can validate, and this project's own standard for that (follow-ups
3b and 19) is to name it rather than guess. Follow-up 23.

**5. `_route_knobs` silently dropped a duplicated knob.** `--knob bank_reserve=1 --knob
carpenter:bank_reserve=2` are different parser keys landing on the same role and knob;
last one won and the other vanished. The function was refusing the ambiguous and the
